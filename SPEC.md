# SPEC

## Manager

### Problem
Gavin wants to study Matthew at the sentence level — comparing two Greek editions, several open-source English translations, and his own Claude-generated candidate translations under different prompting and grounding strategies — then rank them and stitch the winners into his own translation (the GSV). No off-the-shelf tool does this: Bible apps don't expose Greek-aligned sentences as ranking units, don't let him generate and provenance-track LLM translations under explicit *(style prompt) × (source set)* combinations, and don't let him author an overlay on red-letter ranges. Doing nothing means he keeps doing this in scratch documents with no provenance, no reproducibility, and no path to a publishable artifact.

### Users
Gavin. One person, one device, no auth, no sharing. Treat every other "user" as out of scope; the static-site export is the only read path for anyone else and it is one-way.

### Success criteria
- Matthew is loaded end-to-end from version-pinned fixtures (SBLGNT, Byzantine, BSB, BLB, BIB, WEB) and SQLite can be deterministically rebuilt from those fixtures.
- Every Greek sentence has a stable ID and a span in **SBLGNT** (the canonical sentence model in v1); the verse range it covers; a `starts_at_verse_boundary` flag; and per-translation English spans. **Byzantine ships as verse-keyed reference text** retrievable for the verse range covered by each sentence. **Full Byzantine sentence-boundary alignment is deferred to v2.**
- Gavin can open a sentence and see, side by side: SBLGNT, the Byzantine text covering the same verse range, every loaded English translation (including WEB as a parallel reader column), and any Claude-generated candidates for that sentence. **WEB renders in the static-site parallel reader column as well as the local UI.**
- Red-letter ranges are imported (Berean source if available, hand-curated otherwise) and Gavin can split / merge / extend / retract / reject ranges through the UI; edits persist as an overlay and never mutate the imported fixture; each range carries provenance (origin + modification history).
- At least **three** seeded style-prompt artifacts (`literal-v1`, `dynamic-v1`, `plainspoken-v1`) round-trip through Claude under at least **two** Greek-grounded source sets (`SBLGNT_ONLY` and `BOTH_GREEK`); every candidate is stored with `(style_prompt_version, source_set, model, timestamp)` plus the resolved source documents — fully reproducible, fully traceable.
- Gavin can rank the candidates (Greek editions + open-source English + Claude candidates) per sentence, and rankings persist.
- The GSV for Matthew can be exported in **three** formats — (a) plain text, (b) structured JSON naming the winning source per sentence, (c) Markdown with chapter headers and per-sentence provenance footnotes — every sentence traceable to either an open-source translation + verse range, or a (prompt version, source set, model, timestamp).
- A static site can be built from SQLite with at minimum: parallel reader, red-letter focus view, and GSV view.
- Matthew 5 (Sermon on the Mount) works end-to-end through every workflow above before anything else is generalized.

### Accepted v1 narrowing (deviation from CLAUDE.md JTBD framing)
CLAUDE.md JTBD #1 and the Alignment section say "the Greek span in each edition (SBLGNT and Byzantine) — they may diverge; record both spans" and "Mismatches between SBLGNT and Byzantine sentence boundaries are themselves data — record them, don't hide them." **In v1 we accept a narrower scope than that framing implies.** Specifically:
- Sentence IDs and sentence-level spans are SBLGNT-only.
- Byzantine is stored at verse granularity and rendered as reference text per the verse range each SBLGNT sentence covers.
- Where the SBLGNT sentence's verse range visibly crosses a Byzantine sentence break, the UI surfaces a "boundaries diverge" indicator (Designer's `↔` glyph) without persisting the Byzantine boundary.
- Byzantine sentence-level alignment ships as additive tables in v2 if Gavin actually needs sentence-keyed Byzantine ranking. Manager view: he won't, until he tries.

The trade-off: cross-edition boundary mismatches are visible (good enough for study) but not fully recorded as structured data (deviation from the JTBD framing). This is an explicit acceptance, not an oversight.

- **Generation may target any sentence in Matthew** (red-letter or not — non-red-letter context is allowed); **ranking and GSV compilation in v1 target red-letter sentences first.** Non-red-letter ranking is allowed but explicitly not required for the v1 DoD.
- Sentence-level ranking workflow and persistence.
- GSV compilation and export in **three formats**: plain text, structured JSON, Markdown.
- Local web UI as the working surface; static-site export as the publishing surface, sharing components where practical.
- SQLite + fixture-file storage with deterministic rebuild.
- An in-UI **Build static site** button that invokes the same pipeline as `make build-static`. The CLI Make target is the primary surface; the in-UI button is a convenience and **is required in v1** so Gavin doesn't have to leave the browser for a publishing run.
- **Optimistic concurrency control on writes** (rankings, red-letter overlays, tie-breaks). Even though only Gavin uses the tool, two open browser tabs are the realistic failure mode and silent last-save-wins would corrupt rankings he can't easily reconstruct. - Any book other than Matthew. Do not generalize the data model yet.
- Ranking / GSV workflow for non-red-letter passages as a v1 DoD requirement (display for context is fine; ranking *may* target non-red-letter sentences but the DoD is met when red-letter ranking + GSV works).

- WEB as a Claude grounding source (defer; if useful later, add a `GREEK_PLUS_WEB` source set then).
- Hebrew OT, LXX, audio.
- Multi-user, auth, sharing, accounts, SEO, analytics.
- Mobile / Expo client. The static site covers external reading.
- Untraceable text anywhere in the GSV — every GSV sentence must resolve to either an open-source translation + verse range or a (prompt version, source set, model, timestamp).

## Designer

### Surfaces

- **Local web UI (working surface)** — single-user, served from FastAPI on `localhost`. Read/write. The only place ranking, red-letter editing, and Claude-candidate generation happen.
- **Static site (publishing surface)** — read-only build artifact rendered from the same SQLite. Mirrors the local UI's reader views (parallel reader, red-letter focus, GSV) but strips every authoring affordance (no edit/rank/generate buttons, no admin nav).
- **CLI / Make targets** — `make import` (rebuild SQLite from fixtures), `make export-gsv` (writes `gsv.txt` + `gsv.json`), `make build-static` (renders the static site). Surfaced because Gavin will run these from the terminal far more often than any UI button would justify.
- **HTTP API** — FastAPI under `/api/v1/*`, consumed by both the local UI and the static-site builder. Pydantic-modelled per global rules. No public surface; bound to localhost.
- **File outputs** — `gsv.txt` (plain), `gsv.json` (structured with per-sentence provenance), and the static site under `dist/`.

Global navigation in the local UI: top nav with five entries — **Read**, **Red Letters**, **Generate**, **Rank**, **GSV**. Plus a persistent breadcrumb showing current chapter:verse and a chapter-jump input (e.g. typing `5:3` jumps to Matt 5:3 in the active surface). A status pill in the corner shows fixture version + last import timestamp so Gavin can tell at a glance whether the DB is fresh. When the pill detects a stale or out-of-date fixture (manifest hash on disk differs from `fixture_version` in DB), it expands on hover to show a **"Re-import fixtures"** button that POSTs `ReimportRequest { force: false }` to `POST /api/v1/admin/reimport` and refreshes the page on success. On a `409` response with `code: "orphans_detected"`, the button does **not** silently succeed and does **not** auto-retry with `force=true`; instead the UI navigates directly to the orphan-resolution screen described under "Fixture version change mid-work" (Edge cases), passing through the `details.orphan_summary` from the 409 body so each orphan is listed with its remap/keep/delete options. Re-import only runs once orphans are resolved (the resolution screen issues a follow-up request with `force=true` once the user has explicitly chosen a disposition for every listed orphan).

**Keyboard shortcut scoping (global rule):** every keyboard shortcut documented below (`j`/`k`, `g`, `r`, `c`, `s`, `n`/`p`, `1`–`9`, etc.) is bound only when focus is **not** inside an `<input>`, `<textarea>`, or `[contenteditable]` element. Typing in the Notes field, the chapter-jump input, or any text input must never trigger a shortcut. The chapter-jump input commits on `Enter`/blur.

### Reference rendering rules (global)

These rules govern how reference text (Byzantine, English translations) is displayed alongside an SBLGNT sentence anywhere in the app. They apply uniformly to **Flow 1's parallel reader rows**, **Flow 1/2's sentence detail drawer**, and **Flow 5's Rank top-strip** — the three surfaces where Gavin reads Byzantine or English text *as reference for an SBLGNT sentence*. Centralised here so changes to the rule don't drift across surfaces.

- **Rule R1 — Partial-verse highlight.** When the focal SBLGNT sentence has `starts_at_verse_boundary=false` *or* `ends_at_verse_boundary=false`, every reference text column (Byzantine, BSB, BLB, BIB, WEB) renders the **full verse(s) the sentence spans**, with the this-sentence portion highlighted and the adjacent-sentence portion muted grey. Without this, the reference column would silently leak adjacent-sentence words and Gavin would be ranking against text that includes content from a *neighbouring* sentence — unacceptable on the rank surface in particular.
- **Rule R2 — Byzantine projection caveat.** Byzantine is verse-keyed (no persisted sentence rows in v1). The highlighted word-range is a best-effort projection from the SBLGNT sentence boundary; the column carries a `≈` glyph and tooltip "Byzantine is verse-keyed; the highlighted span is a best-effort word-range projection from the SBLGNT sentence boundary." If the projection cannot be computed cleanly, the entire Byzantine verse renders muted with the `≈` glyph (consistent with Flow 3's range-editor convention).
- **Rule R3 — English projection caveat.** English translations follow verse boundaries; the highlighted portion approximates this Greek sentence. Tooltip: "English translations follow verse boundaries; the highlighted portion approximates this Greek sentence."
- **Rule R4 — Clean case is unmarked.** When `starts_at_verse_boundary=true` *and* `ends_at_verse_boundary=true`, no muting and no `≈` glyph — every reference column shows just the sentence's verse(s) verbatim.
- **Rule R5 — SBLGNT itself is exempt.** SBLGNT is the canonical unit; its rendered span is exactly the sentence's words, never expanded to full verse.

### Primary flows

#### Flow 1 — Parallel reader (Read)
1. Gavin opens **Read** → defaults to Matthew 1, or the last chapter he viewed (persisted in `localStorage`).
2. Page renders a vertically scrolling list of **sentences** (the atomic unit). Each sentence is a row containing columns: **SBLGNT**, **Byzantine**, **BSB**, **BLB**, **BIB**, **WEB** (if loaded). Column visibility is toggled in a sticky header; toggle state persists. **Every reference column (Byzantine, BSB, BLB, BIB, WEB) follows the Reference rendering rules R1–R5 above** — partial-verse rows show full verse with this-sentence portion highlighted and adjacent muted; clean rows are unmarked.
3. Each sentence row shows: the sentence ID (small, monospace), the verse range it covers (e.g. `5:3–5:4`), and a `⚓` glyph if `starts_at_verse_boundary` is true (a glyph, not a word — the clean case is the boring case).
4. Red-letter sentences have a left-edge red rule. Clicking the rule deep-links to that specific sentence in the **Red Letters** view (opens in a new tab, the target row is scrolled into view and momentarily highlighted, and the sentence detail drawer auto-opens to the range editor).
5. Clicking any sentence row opens a **sentence detail drawer** (right side, ~40% width) with: full Greek span per edition, every English translation in full, any Claude candidates already generated, an existing ranking if one exists, and three primary actions: **Generate candidate**, **Rank this sentence**, **Edit red-letter range**. The drawer's reference text columns also follow Reference rendering rules R1–R5.
6. Keyboard: `j`/`k` next/previous sentence, `g` then `5` jumps to chapter 5, `r` opens the rank action, `c` opens generate-candidate.

#### Flow 2 — Red-letter focus view (Red Letters)
1. Gavin opens **Red Letters** → list of every sentence that intersects the effective red-letter set (`Berean source ∪ Gavin's overlay`), in canonical order.
2. Each row shows: sentence ID, verse range, the BSB English (the most readable open-source rendering), and provenance badges — `Berean`, `manual`, or `Berean + manual edits` — with a hover tooltip listing modification history.
3. Filters in the sticky header: **Source** (Berean / manual / both), **Has Claude candidates** (yes / no), **Has ranking** (yes / no / partial), **Chapter** (1–28).
4. Clicking a row opens the same sentence detail drawer as Flow 1, but defaulted to the **range editor** tab so editing is one click away.
5. An **"Add range"** button at the top lets Gavin mark a previously non-red sentence (or sub-span) as red-letter — opens the range editor with a fresh range scoped to the currently visible chapter.

#### Flow 3 — Red-letter range editor (highest-stakes UX)
The editor is a modal/drawer pinned to a single Greek sentence, but a range may span multiple sentences. The unit being edited is a **range** (a contiguous Greek span tagged as Jesus-speech), not a sentence — but the editor is always anchored on a sentence so Gavin sees the textual context.

Layout:
- **Left pane**: vertical list of the 5 sentences before, the focal sentence, and the 5 sentences after — Greek (SBLGNT by default, Byzantine toggle), with the current effective red-letter span shaded red.
- **Right pane**: range metadata — origin badge (`Berean`/`manual`), start sentence, end sentence, start word offset, end word offset, modification history (timestamped list of prior edits).
- **Bottom action bar**: five buttons — **Split**, **Merge**, **Extend**, **Retract**, **Reject** — plus **Save** and **Cancel**.

Operations:
1. **Split** — Gavin clicks a word inside the shaded span; a divider appears at that word; clicking **Split** creates two ranges with the divider as the boundary. Confirmation step shows the resulting two ranges' Greek + BSB before persisting.
2. **Merge** — enabled **only when two ranges are touching at the word boundary, OR separated only by whitespace and/or punctuation tokens with no intervening non-Jesus word**. Two non-contiguous ranges within the focus window (i.e. separated by one or more Jesus-eligible words that are *not* tagged red) **cannot** be merged from this UI — merging across a real gap would invent Jesus-speech in that gap. If Gavin wants to bridge a true gap he must first **Extend** one range to cover the gap, then **Merge**. When Merge is disabled, hovering it shows the reason ("not adjacent — extend across the gap first"). On a valid merge, one click combines the two ranges, picking the earlier start and the later end; the merged range's modification history concatenates both source histories.
3. **Extend** — Gavin clicks a word outside the current shaded span (within the focus window); preview shades the new boundary; confirm to persist. Extension may span multiple sentences within the same chapter — UI explicitly shows that the range now spans N sentences. **Extension may not cross a chapter boundary** in v1; if Gavin clicks a word in another chapter, the click is rejected inline (see Error states).
4. **Retract** — Gavin clicks a word inside the current shaded span; preview shows the new (smaller) shaded region; confirm to persist. Retraction down to zero words is the same as **Reject**.
5. **Reject** — single click; confirmation modal: "Reject this range? It will remain in history but will not contribute to the effective red-letter set." Rejection writes a `rejected=true` overlay record; the source range is not deleted (overlay-only mutation per JTBD #2).

Rules:
- A range may span multiple sentences **within a single chapter**. Cross-chapter ranges are not supported in v1.
- Every operation creates a new overlay record; the imported fixture is never mutated. Visible affordance: an **"Original" diff toggle** in the right pane that re-renders the focal area as it would look with overlay disabled. For a range with `origin=manual` (no fixture source to diff against) the toggle is greyed out with the tooltip "no source — entirely manual."
- Save is atomic per operation. If the user has staged a Split but not yet saved, navigating away prompts: "Discard pending range edit?"
- Word-level boundaries are anchored to the **SBLGNT** word index (the canonical edition for ranges). When Byzantine is shown, the editor highlights *approximately* the same span using sentence-aligned mapping; if no Byzantine word maps cleanly, a small `≈` glyph appears on the Byzantine pane indicating "this is a best-effort visualisation, the canonical range is on SBLGNT."

#### Flow 4 — Claude-translation generator (Generate)
1. Gavin opens **Generate** → top of page is a **batch form**, below is a list of recent generation runs.
2. Batch form fields:
   - **Scope**: dropdown — *one sentence* (text input for sentence ID), *verse range* (e.g. `5:3-5:12`), *whole chapter* (1–28), *all unranked red-letter sentences*.
   - **Style prompt**: dropdown of versioned prompts (`literal-v1`, `dynamic-v1`, `plainspoken-v2`, `first-century-jewish-v1`, `poetic-v1` …). Each entry shows version + last-modified date. A **"View prompt"** link opens the prompt source read-only.
   - **Source set**: checklist with mutually-meaningful presets — *SBLGNT only*, *Byzantine only*, *Both Greek*, *Greek + BIB*, *Greek + BLB*, *Greek + BSB*, *English only (BSB)* (flagged with a warning glyph: "no Greek; reference-only").
   - **Model**: dropdown — defaults to current Claude model; older selections grey out but remain selectable for reproducibility.
3. **Scope summary** (inline, no button) — before any subagent is spawned, the form shows **the resolved sentence count and an estimated wall-clock duration** for the chosen scope, recomputed live as Gavin changes the scope dropdown. Format: `~{seconds}s/sentence × {N} sentences ≈ {minutes} min`. The per-sentence figure is the rolling median of recent worktree wall-clock latencies (or a fixed default — e.g. 35s — until enough runs exist to compute one); concurrency from `MAX_CONCURRENT_WORKTREES` is factored in so the indicator reflects elapsed time, not summed CPU. The contract: Gavin sees how many worktrees he is about to spawn and roughly how long he'll wait, before committing. There is no dollar figure — generation runs against Gavin's existing Claude Code subscription, not a per-token meter.
4. **Duplicate-batch soft warning** — on clicking **Generate**, if the same `(style_prompt_version, source_set, model)` combo was already run for any sentence in the current scope within the last hour (configurable), an inline confirm prompt surfaces: "N of the M targeted sentences already have a candidate from this combo within the last hour. Continue anyway?" Two buttons: **Continue** (proceeds), **Review existing** (links to the rank view filtered to the affected sentences). This is a soft warning, never a block — Gavin sometimes wants intentional re-runs.
5. **"Generate"** button — submits the batch; UI navigates to the run detail page with a streaming progress list (sentence-by-sentence, one row per sentence as it completes). Each completed row shows: sentence ID, the new candidate text, latency, and a "View in Rank" link. The run detail page also exposes a **Cancel** button at the top: clicking it stops further sentence dispatch (in-flight worktree subagents are allowed to finish so their work isn't thrown away; their results still persist). After cancel, the run is marked `cancelled` and the unprocessed sentences show a `— skipped (cancelled) —` row with a **Resume** affordance that re-submits only the unfinished slice.
6. Each candidate is stored with `{style_prompt_version, source_set, model, timestamp, sentence_id}` — these five fields are the candidate's identity and they're shown verbatim in any UI that displays the candidate.
7. Re-generating the same `(sentence, prompt, source set, model)` tuple does **not** overwrite — it creates a new candidate with a new timestamp. Gavin can compare runs of "the same combo, different days."

#### Flow 5 — Ranking workflow (highest-stakes UX, alongside the range editor)
Ranking is per-sentence. The screen is built around comparison density: Gavin needs to see every option for one sentence at once, drag them into order, and move on quickly to the next sentence.

Layout (single sentence at a time):
- **Top strip (sticky)**: sentence ID, verse range, `starts_at_verse_boundary` flag, both Greek spans (SBLGNT and Byzantine), in a compact two-column block. This is the reference text — never moves. **The Byzantine column in this strip follows Reference rendering rules R1–R5**: when the focal sentence has `starts_at_verse_boundary=false` or `ends_at_verse_boundary=false`, the Byzantine column renders the full verse(s) with the projected word-range highlighted and adjacent words muted (with the R2 `≈` caveat). Without this rule the rank surface — where Gavin makes ranking decisions against the reference text — would silently leak adjacent-sentence Byzantine words.
- **Main area**: a vertical list of **candidate cards**, one per option. A card carries: a draggable handle, a rank number badge, the candidate text (multi-line, full sentence), and a provenance footer:
  - For open-source translations: name + verse range (e.g. `BSB · 5:3`).
  - For Claude candidates: `claude · ${style_prompt_version} · ${source_set_label} · ${model} · ${timestamp}`.
- **Right rail**: an **"Unranked"** holding column. New candidates land here. Cards in Unranked do not contribute to the GSV.
- **Bottom action bar**: **Save ranking**, **Skip (mark as unrankable)**, **Next sentence** (`→` / `n` key), **Previous sentence** (`←` / `p` key).

Interactions:
1. Drag-and-drop reorders cards. Keyboard alternative: `↑`/`↓` with a focused card moves it; `1`–`9` jump-assigns the focused card to that rank; `j`/`k` move focus between cards without reordering; `h` hides the focused card; `c` toggles the focused card's compare-checkbox.
2. **Tie support**: dragging a card directly onto another card (rather than between cards) creates a tie — both cards display the same rank number with a `=` glyph (`1=`). Ties are first-class; the GSV compiler must resolve them (see Flow 6).
3. **Hide button** per card — moves the card to a collapsed "hidden" tray at the bottom of the page. Hidden cards persist as `excluded=true` so they don't reappear after re-generation. (Useful for a Claude candidate that's just bad — Gavin shouldn't have to keep seeing it.) **Hidden Claude candidates still count toward "has Claude candidates"** for the rank-queue filter — that filter answers "did a Claude candidate ever exist for this sentence?", not "is one currently visible?".
4. **Compare two**: clicking two cards' compare-checkboxes opens a side-by-side diff modal (word-level diff highlighting). Useful for distinguishing near-identical candidates.
5. **Notes** field per sentence — a free-text textarea persisted with the ranking (e.g. "BLB wins on θεῷ but BSB reads better aloud"). Optional. While focus is in this textarea, all keyboard shortcuts are disabled per the global scoping rule above.
6. **Save** is required to commit. Until saved, a sticky "unsaved changes" banner persists; navigating away prompts.
7. After **Save**, "Next sentence" auto-advances to the next sentence with no saved ranking (skipping already-ranked ones unless toggled). Gavin can rank an entire chapter without touching the mouse.

**Keyboard cheat-sheet (mouse-free ranking, shown in a `?` overlay):**
- `j` / `k` — focus next / previous card
- `↑` / `↓` — move focused card up / down
- `1`–`9` — assign focused card to that rank
- `t` — tie focused card with the card immediately above it
- `h` — hide focused card
- `c` — toggle compare-checkbox on focused card
- `s` — **Save** the current sentence's ranking
- `n` / `→` — Save (if dirty) and advance to next unranked sentence
- `p` / `←` — previous sentence (prompts if unsaved)
- `x` — Skip / mark unrankable
- `?` — toggle this cheat-sheet
- All shortcuts are disabled while focus is in the Notes textarea or any other text input (global scoping rule).

A **"Rank queue"** index page (`/rank/queue`) lists every sentence with a status badge: *unranked*, *partial*, *ranked*, *skipped*. Filterable by chapter, by red-letter status, and by "has Claude candidates" (which, per #3 above, counts hidden Claude candidates as present). This is the entry point Gavin will use most.

#### Flow 6 — GSV compilation and export
1. Gavin opens **GSV** → renders the current GSV: per-chapter accordion, with each sentence shown as the winning candidate's text, plus a thin provenance line beneath. **Unranked sentences in partially-ranked chapters render as a muted placeholder** (`— unranked —`) with a **Rank now** link that deep-links to that sentence's rank page — matching the static-site build's behaviour exactly so the local view never disagrees with `dist/`.
2. **Coverage indicator** at the top: "Matthew GSV: `{ranked}` / `{total}` sentences ranked (Matthew 5: `{ch5_ranked}` / `{ch5_total}`)." A chapter heat-strip shows ranking density per chapter (1–28). All counts come from the live DB; no number is hardcoded in the UI.
3. **Tie resolution**: when a sentence has tied top-rank candidates, the sentence appears with an inline warning (`⚠ tie — pick a winner`). Clicking it opens a tie-breaker modal showing only the tied candidates; Gavin picks one. The pick is recorded with reason: *tie-broken-by-Gavin* + timestamp. Until broken, the sentence renders as `[TIE: see Rank]` in the GSV view and is omitted from the plain-text export.
4. **Export** dropdown:
   - *Plain text* — `gsv.txt`, just the prose, chapter:verse markers, no provenance.
   - *Structured* — `gsv.json`, every sentence as `{sentence_id, verse_range, text, provenance}` where provenance is one of `{kind: "translation", name, verse_range}` or `{kind: "claude", style_prompt_version, source_set, model, timestamp}`.
   - *Markdown* — readable middle ground (chapter headers, sentence-level footnotes for provenance).
5. **Build static site** button — POSTs `BuildStaticRequest { include_unranked_placeholders: bool }` to `POST /api/v1/admin/build-static`, which runs the same builder as `make build-static` and renders parallel reader, red-letter focus, and GSV views into `dist/`. UX contract:
   - **Options inline with the button**: a checkbox **"Include unranked placeholders"** (default **on**) sits immediately to the left of the Build button. Hover help: "Off: skip sentences with no saved ranking. On: render them as `— unranked —` placeholders so partial coverage is still publishable." The checkbox state is the `include_unranked_placeholders` field on the request.
   - **In-flight state**: on click, the button is disabled, label changes to **"Building…"** with an inline spinner, and the checkbox is locked. Other GSV controls remain interactive (Gavin can scroll, expand chapters); only the build trigger is gated.
   - **Success state**: on 2xx, an inline result block appears beneath the button surfacing every field of `BuildStaticResponse`, formatted to mirror the in-app GSV coverage indicator from step 2 — e.g. **"Built `dist/` — 142 / 384 sentences ranked (Matthew 5: 18 / 24), 24 files, 1.8s."** The `dist_path` is shown verbatim as a monospace path with a copy-to-clipboard icon. The block persists until the next build click. If `include_unranked_placeholders=false` was used and `coverage.ranked < coverage.total`, an inline note adds: "`{total - ranked}` unranked sentences were skipped from the build."
   - **Failure state**: covered in Error states (surfaces the underlying error from the response body).

### Error states

- **Fixture import failure** — landing page shows a red banner: "Fixture import failed at `${fixture_name}`. SQLite may be partial. Run `make import` again or check the import log at `${path}`." All authoring routes (Generate, Rank, edit endpoints) return a 503 with a structured error and the UI disables the corresponding nav items rather than letting Gavin write into a half-loaded DB.
- **Sentence not found** (deep-link to a sentence ID that doesn't exist in current fixtures) — empty state: "Sentence `${id}` is not in the current fixture set. It may have been removed or the fixture version changed. Current fixture: `${fixture_version}`." Single action: "Go to Read."
- **Claude generation failure** (subprocess timeout, invalid response, worktree spawn error, internal) — the failed sentence row in the run detail page goes red with the error message; other sentences in the batch continue. Action: **Retry this sentence**. Per Architect, Retry dispatches a fresh single-sentence run with a new `run_id` and `parent_run_id` pointing at the original run. **View behaviour after click (option a — transparency):** Gavin **stays on the original run's detail page**; the failed row remains visible in its red error state (now stale — that attempt is over) and a new sticky inline link appears at the top of the page: **"Retry queued — view new run →"** linking to the new `run_id`'s detail page. The new candidate, when it arrives, streams via SSE into the **new** run's detail page, not the original. Rationale: silently swapping a failed row for a successful one (option c) hides the failure history Gavin may want to inspect; force-navigating away (option b) interrupts him if he was reading other rows. The link is the explicit handoff. Failed candidates are *not* written to the DB; only successful generations persist.
- **Claude Code subagent returns empty / unparseable output** — treated as failure (`error_code='invalid_response'`), not a stored candidate. Surface the captured stderr or the truncated stdout verbatim in the UI so Gavin can debug the prompt or rerun.
- **Range editor: invalid boundary** — inline error in the right pane covering several conditions:
  - Start ≥ end: "Range cannot end before it begins."
  - Extension click landed in a different chapter than the focal range: "Cross-chapter ranges are not supported in v1. A range may span multiple sentences within a chapter, but cannot cross a chapter boundary." The clicked word is *not* added to the preview; Save is unaffected (no invalid state was committed to the preview).
  - Merge attempted on non-adjacent ranges: button is disabled with hover tooltip "not adjacent — extend across the gap first" (see Flow 3). No error toast — the disabled state is the affordance.
  Save button disabled while any inline error is present.
- **Range editor: word index out of range on Byzantine** — toast: "This boundary doesn't map cleanly to the Byzantine edition. The range is anchored on SBLGNT; the Byzantine highlight is approximate."
- **Ranking save conflict** — concurrent save (e.g. another tab) detected by version mismatch: modal "This sentence's ranking was changed in another tab. Reload to see latest, or overwrite?" Two buttons: **Reload**, **Overwrite**.
- **Tie left unbroken at export** — `make export-gsv` exits non-zero with a list of unbroken-tie sentence IDs. The plain-text export refuses to write; the structured export writes with `provenance: {kind: "tie", candidates: [...]}` and a top-level `unresolved_ties` array so Gavin can see what's missing.
- **Static-site build with partial coverage** — succeeds, but each unranked sentence renders in the GSV view as a muted placeholder (`— unranked —`) with a link back to the local UI's Rank page. The build log prints a coverage summary.
- **Static-site build failure (in-UI Build button)** — on a non-2xx response from `POST /api/v1/admin/build-static`, the in-flight state clears, the button re-enables, and an inline error block replaces the success block: "Build failed: `${error_message}`." The block includes a **"Copy error"** affordance and a **"View server logs"** link to wherever the API surfaces its log path. The checkbox state and any partial `dist/` are left as-is — Gavin re-runs `make build-static` from the terminal if he needs to debug.
- **No Claude candidates yet for a sentence** — once fixtures are loaded, every sentence already has the open-source candidates (BSB, BLB, BIB, WEB, plus the two Greek editions) — there is no "zero candidates" state under normal conditions. The legitimate "thin" state is *no Claude candidate exists yet*. The Rank page surfaces this as a top-of-card prompt: "No Claude candidates yet — generate one from this sentence's row." Single button: **Generate from this sentence** (opens Flow 4 prefilled with `scope=one sentence` and this sentence ID). Open-source candidates remain rankable on their own; ranking without any Claude candidate is a valid Save.
- **Zero candidates at all (degenerate)** — only reachable if fixtures failed to import for this sentence. Rank page shows: "No candidates available. The fixture import may be incomplete — re-import from the status pill." Single button labelled **"Re-import fixtures"**: clicking it scrolls the status pill into view, expands the pill's hover panel programmatically (so it stays open without a hover), and moves keyboard focus to the pill's **"Re-import fixtures"** button (it does **not** auto-submit). This keeps a single submit path — the status-pill button — so the orphan-resolution branch from Surfaces (409 → orphan-resolution screen) works identically whether the user starts from the rank empty state or the pill itself. Direct-POST from the empty state was rejected because it would duplicate the 409-handling logic on a second code path.
- **Network/API down** (local FastAPI not running) — UI shell shows a persistent banner "API offline — `make dev` to start the server." All write actions are disabled; reads from cached page state remain visible.

### Empty states

- **Fresh DB, no Claude candidates anywhere** — Generate page shows a one-paragraph onboarding: "No candidates yet. Pick Matthew 5 as your first batch — it's the proving ground." with the form prefilled to *whole chapter = 5*, *style = literal-v1*, *source set = Both Greek*. Directly beneath the form, a persistent **DoD hint banner** reads: "**Matthew 5 DoD requires all three seeded prompts.** After this run, re-submit the same scope with `dynamic-v1` and `plainspoken-v1` to satisfy the chapter-5 end-to-end target." The banner has a small **"Why three?"** info popover linking to the DoD line in `SPEC.md` and a **dismiss-for-this-session** affordance (state held in `sessionStorage`, not persisted across browser restarts — re-appears on each fresh session until all three prompts have at least one candidate apiece for Matthew 5, at which point the banner auto-hides). **Auto-hide counts candidate *existence*, not visibility**: a candidate row in `claude_candidates` for `(prompt_version, sentence in Matthew 5)` satisfies the check even if Gavin has hidden it via the rank UI's hide affordance (`excluded=true`). This matches the rank-queue filter semantics from Flow 5 #3 ("did a Claude candidate ever exist for this sentence?"). So once Gavin has run all three seeded prompts at least once over Matthew 5, hiding individual combos in the rank UI does **not** make the banner re-appear. I picked option (b) (banner + auto-hide on completion) over option (a) (prefill all three) because Flow 4's batch form is single-select on style prompt, and forcing multi-prompt batches would either complicate the form schema or fan out into three queued runs the user didn't explicitly opt into. A banner keeps the user in control while making the DoD coupling impossible to miss.
- **Rank queue with everything unranked** — instead of a list of zeros, show a "Start with Matthew 5" CTA that filters the queue to chapter 5 red-letter sentences.
- **GSV with zero ranked sentences** — large empty state: "Rank some sentences to start building the GSV. Matthew 5 is a good place to start." Single CTA → Rank queue filtered to Matthew 5.
- **Red Letters view with no overlay edits yet** — list still populates from Berean source; a small banner notes "All ranges from Berean source — no manual edits yet."
- **Red Letters view with no Berean tagging available** (verification item from TODO) — empty state: "No red-letter source ingested. Hand-curate ranges to begin." with an **"Add range"** button. The data-loading status pill flips to indicate fallback mode.

### Edge cases

- **SBLGNT vs Byzantine boundaries diverge (verse-range overlap heuristic)** — Byzantine in v1 is verse-keyed only (no Byzantine sentence rows persisted; sentence-level Byzantine alignment is deferred to v2 per Architect). The parallel reader detects divergence using verse-range overlap on the SBLGNT sentences alone:
  - If two adjacent SBLGNT sentence rows share at least one Byzantine verse (i.e. their verse ranges overlap on the same verse number), or
  - If an SBLGNT sentence ends mid-verse (`ends_at_verse_boundary=false`) where the Byzantine verse-text continues uninterrupted into the next SBLGNT sentence,
  then a `↔` glyph appears between the two affected rows and both rows surface a "boundaries diverge — Byzantine is verse-keyed; sentence split is approximate" hover note. Ranking remains per-SBLGNT-sentence (the canonical unit); Byzantine is presented as reference. v2 introduces persisted Byzantine sentence rows; the heuristic is replaced with a precise two-sentence comparison at that point.
- **Sentence does not start at a verse boundary** (`starts_at_verse_boundary=false`) — covered by the **Reference rendering rules R1–R5** subsection above (the canonical statement of the partial-verse rule). The rule applies uniformly to the parallel reader (Flow 1), the sentence detail drawer (Flow 1/2), and the Rank top-strip (Flow 5) — every surface where reference text accompanies an SBLGNT sentence. Without this rule the Rank top-strip's Byzantine column, in particular, would silently leak adjacent-sentence words into Gavin's ranking decision.
- **Sentence spans multiple verses across a chapter boundary** — verse range displays as `5:48–6:1`; the parallel reader breaks the row across the chapter rule with a visible chapter header inside the row.
- **Berean red-letter tagging missing entirely** — fall back to manual mode (per JTBD #2). UI behaviour is identical except every range starts with `origin=manual`.
- **Berean tagging present but partial** — sentences without imported red-letter tagging show a `?` provenance badge in the Red Letters view. Sorting by "needs review" surfaces them.
- **Ranking ties** — first-class. UI displays `1=`, `1=`, `2`, etc. GSV resolution requires explicit tie-break (Flow 6). Export to plain text refuses on unbroken ties; structured export records the tie.
- **Single-candidate ranking (degenerate)** — under normal conditions every sentence has at least the open-source translation candidates (BSB, BLB, BIB, WEB, plus the two Greek editions), so the "exactly one candidate" state is unreachable except when Gavin has explicitly hidden every candidate but one. In that edge case the rank UI shows the lone card pre-ranked at #1 with a "trivial — all others hidden" badge and a link to the hidden-cards tray; Gavin must still click **Save** to commit. Trivial rankings are never auto-saved.
- **Re-generated identical candidate** — same `(sentence, prompt, source set, model)` produces a new candidate with a fresh timestamp; the rank UI groups them under a "n runs of this combo" expandable; the most recent is surfaced by default.
- **Long sentences** (e.g. extended discourse with no period for several verses) — sentence detail drawer is scrollable; rank cards expand to fit; export preserves the sentence as a single unit. The parallel reader row is allowed to grow tall — no truncation, since truncation would hide variant text that's the whole point.
- **Very short sentences** (single-word exclamations, vocatives) — same treatment; rank UI and provenance footers do not collapse.
- **Partial Matthew coverage** — every read view (parallel reader, red-letter, GSV) is well-defined for any subset of Matthew. Coverage indicator is always visible. Static-site build never fails on partial coverage; it renders placeholders.
- **Fixture version change mid-work** — if the import script bumps the fixture version while there are unsaved or in-flight candidates/rankings tied to old sentence IDs, the import script refuses to overwrite without `--force`, and the API returns `409 { code: "orphans_detected", details: { orphan_summary: ... } }`. Both entry points trigger the same orphan-resolution screen:
  - **From the status pill** (Re-import button): the 409 navigates the user to the resolution screen instead of silently succeeding (see Surfaces above).
  - **From `make import`** (CLI): the script exits non-zero and prints "Fixture upgrade pending. Resolve `${n}` orphaned candidate(s) first — open the local UI's status pill or visit `/admin/orphans`."
  Orphan resolution is a manual review screen listing each affected candidate with options: *remap to new sentence ID*, *keep with old ID (read-only)*, *delete*. Once every orphan has an explicit disposition, a sticky **"Apply and re-import"** button at the bottom commits the dispositions and re-issues `POST /api/v1/admin/reimport` with `force=true`. Until every orphan is resolved the button is disabled.
- **Same English translation maps to multiple sentences (verse spans 2 sentences)** — display shows the full verse text in each affected sentence's row, with the relevant portion highlighted differently in each. The translation can be ranked in either sentence independently; the GSV compiler accepts the same source-translation+verse-range for two adjacent sentences without complaint, but flags it in the structured export.
- **Concurrent edits from two browser tabs** — last-save-wins is unacceptable for ranking and range edits. Every write carries an `If-Match` style version; conflicts surface a modal (see Error states).
- **Static-site build clobbering local edits** — `make build-static` writes only to `dist/` (gitignored or version-controlled separately); never mutates SQLite. Re-buildable from SQLite at any time.

## Architect

### Overview

The system is a single-process FastAPI application bound to `localhost`, serving an HTTP API plus a co-located web UI built from React + TypeScript components. SQLite is the single source of truth at runtime; fixture files in the repo are the durable source of truth (SQLite is rebuildable from fixtures, deterministically). A static-site builder consumes the same SQLite via the **service layer** that backs the API (same Pydantic schemas), rendering the read-only view set into `dist/`. There is no auth, no network surface beyond `127.0.0.1`, and no background-job tier — long Claude generations run as in-process async tasks with progress streamed over Server-Sent Events.

This is a deliberately small architecture. Single user, single device, one book — anything more elaborate is rope to hang ourselves with.

### Components

- **`fixtures/`** (filesystem, version-controlled): JSON/YAML files for SBLGNT, Byzantine, BSB, BLB, BIB, WEB; a `manifest.json` pinning URL + retrieval date + release tag + SHA-256 per file; versioned style-prompt artifacts under `fixtures/prompts/`; **a hand-curated `red_letter_source_ranges` fixture** under `fixtures/red_letters/` (see Importer for the rationale and Trade-offs for the Berean decision); optional Berean machine-readable red-letter source if/when verified. Boundary: read-only at runtime, mutated only via deliberate ingestion-pipeline updates with a fixture-version bump.

- **Importer (`scripts/import.py`)**: Idempotent CLI that reads `fixtures/manifest.json`, verifies SHA-256 per file, and loads everything into SQLite. Drops and rebuilds source-text tables on each run; preserves overlay tables (red-letter overlays, candidates, rankings) and refuses to run when those tables reference sentence IDs that no longer exist unless `--force` is passed (orphan-resolution flow lives in the UI per Designer). Exposed as `make import` and as the `POST /api/v1/admin/reimport` endpoint (see Contracts) so Designer's status-pill action and CLI invoke the same code path. **Red-letter source ingest in v1 is the hand-curated `red_letter_source_ranges` fixture**, covering at minimum Matthew 5; if a Berean machine-readable red-letter distribution is later verified (TODO.md item), an additional importer module replaces the fixture with no schema change. Boundary: writes SQLite, never reads it back during import; never calls the network.

- **Sentence segmenter (`scripts/segment.py`)**: Run as part of import. **SBLGNT path uses the edition's punctuation directly to produce canonical sentences.** **Byzantine sentence-level alignment is explicitly deferred in v1**: Byzantine ships as a verse-level reference text only — its full text is stored, queryable per-verse, and rendered in the parallel reader and detail drawer, but it does **not** receive sentence-boundary rows. All sentence IDs and ranking units are SBLGNT-canonical (see Hard decision #1). When the parallel reader and drawer render Byzantine alongside an SBLGNT sentence, they pull the Byzantine text covering the same verse range; if that verse range crosses what would be a Byzantine sentence boundary, Designer's `↔` glyph still surfaces it as "boundaries diverge" without the boundaries themselves being persisted. Output is the canonical `sentences` table (SBLGNT spans only) plus a `byzantine_verses` table keyed by `(chapter, verse)`. Boundary: pure function from fixture text to sentence/verse rows; no DB writes outside the import transaction.

- **Word tokenizer (part of segmenter)**: Produces a `words` table keyed `(sentence_id, ordinal)` with columns `text`, `strong_id` (nullable, populated when BIB alignment provides one), `byte_start`, `byte_end` (offsets within the sentence text). **Tokenization rule (deterministic)**: a word is a maximal run of Greek letters with diacritics preserved (Unicode categories `L*` and `M*` over the Greek and Coptic / Greek Extended ranges); punctuation and whitespace are word boundaries; clitics joined by an apostrophe (`U+2019` or `U+0027`) — e.g. `δι᾽` — form a single word. Numerals and Latin-script tokens are not expected in SBLGNT but if present are tokenized as Greek words for safety. The same rule is applied to Byzantine for verse-level word counts where useful, but Byzantine words are not tied to SBLGNT word ordinals. The range editor's `(start_sentence_id, start_word_offset, end_sentence_id, end_word_offset)` schema and the BIB alignment both consume the SBLGNT `words` table; word offsets are the `ordinal` column.

- **Aligner (`scripts/align.py`)**: Run as part of import. Consumes BIB's Strong's-keyed interlinear (see Integrations for the pinned schema) to populate `words.strong_id` for SBLGNT words and to produce a per-word English gloss table. For Byzantine, no word-level alignment is produced in v1 (deferred per Hard decision #8); the parallel reader's `≈` glyph remains as the visible affordance for "Byzantine highlight is approximate." Boundary: produces alignment rows; never modifies source-text or sentence tables.

- **SQLite database (`data/bible_study.db`)**: Single file, gitignored. Contains: source texts (per edition), sentences (SBLGNT-canonical) with their Greek spans, `byzantine_verses` keyed by `(chapter, verse)`, the `words` table, per-translation English spans, BIB Strong's-keyed alignment, red-letter source ranges, red-letter overlay ranges, Claude candidates (with surrogate `candidate_id` PK), `source_snapshots` (content-addressed resolved-source bundles, see Contracts), `hidden_combos` (per-sentence-and-combo suppression predicate, see Contracts), rankings, ranking notes, tie-break decisions, `generation_runs` (one row per run) and `generation_run_items` (one row per sentence within a run). Detailed schema is Data engineer's territory in PLAN; here we lock the high-level partition: **immutable-from-fixtures tables** (rebuilt on import) vs **overlay tables** (preserved across imports). Boundary: accessed only through the repository layer; no raw SQL in routes.

- **FastAPI app (`api/`)**: Routes grouped by feature — `api/read/`, `api/red_letters/`, `api/generate/`, `api/rank/`, `api/gsv/`, `api/admin/`. Each feature directory contains `routes.py`, `schemas.py` (Pydantic models for requests/responses, colocated per global rules), and `service.py` (business logic — the layer the static-site builder calls directly). Every route has `response_model=...`; every body is a Pydantic model; full type hints. Mounted at `/api/v1/*`. Boundary: depends on the service layer (which depends on the repository layer); never touches fixture files directly; never makes outbound HTTP except through the Claude client.

- **Repository layer (`api/db/`)**: Thin functions returning Pydantic models (not ORM rows). Uses raw SQL via `sqlite3` or `aiosqlite` — no ORM. Centralised here so swapping SQLite later is contained. Boundary: only place that opens DB connections; route/service code never imports `sqlite3`.

- **Claude Code worktree spawner (`api/claude/`)**: Per-sentence subagent invoker. Takes `(sentence_id, style_prompt_version, source_set_id, model, effort)`, fetches the prompt artifact + the requested sources from the repository, composes the bundle into an `input.md` written to a fresh per-run-per-sentence git worktree at `data/worktrees/{run_id}/{ordinal}/`, spawns `claude -p --model {model} --effort {effort} --output-format text` with `cwd` set to the worktree, captures stdout, and (for prompts whose front-matter declares `output_format: json`) parses stdout as JSON — defensively stripping triple-backtick fences if present. Defaults: `model='claude-opus-4-7'`, `effort='xhigh'`. Computes the canonical SHA-256 of the resolved-source bundle, upserts a `source_snapshots` row (see Contracts), and persists the candidate row pointing at that hash. Cleans the worktree (`git worktree remove --force` + directory wipe) in a finally-block so a crash doesn't leak. Errors raise typed `WorktreeGenerationError(code, message)` with `code` ∈ `{timeout, invalid_response, disk_full, internal}`; run-creation-time failure to find / authenticate the CLI raises `ClaudeCliUnavailableError` (HTTP 400, `code='claude_cli_unavailable'`). Boundary: spawns the local `claude` CLI subprocess; no HTTP outbound. Loads prompt text from `fixtures/prompts/${name}-v${n}.md` — prompt content is fixture, prompt selection is runtime. **Scope summary (Designer's Flow 4 step 3)** is a UI-side derivation from the resolved sentence list and a rolling-median wall-clock estimate; nothing is computed by spawning subagents pre-flight. There is no dollar cost to estimate.

- **Generation runner (`api/runs/runner.py`)**: In-process async task that processes a batch (one sentence to whole chapter) and streams per-sentence progress over SSE using **`sse-starlette`** as the framework integration. Fans out per-sentence work bounded by an `asyncio.Semaphore(MAX_CONCURRENT_WORKTREES)` — concurrency is capped on local worktrees + subprocesses, not on a network connection pool. Each per-sentence task spawns a Claude Code worktree subagent via the spawner above. State is split: the run-level envelope lives in `generation_runs` (status, scope, prompt/source-set/model), and per-sentence state lives in `generation_run_items` keyed `(run_id, ordinal)` with status `pending|running|completed|failed|cancelled|interrupted`, optional `candidate_id`, and `error_code`/`error_message` on failure (full schema in Contracts).
  - **SSE resume-on-refresh**: When a client connects to `GET /api/v1/runs/{run_id}/stream`, the endpoint first **replays all `generation_run_items` rows for that run in `(run_id, ordinal)` order as catch-up SSE events** (one event per non-`pending` row), then attaches to the live in-process broadcast tail for any still-pending sentences. A reconnecting client therefore deterministically reaches the same UI state regardless of when it joined.
  - **Server-restart recovery**: On startup, the runner scans `generation_runs` for rows in `running` status (no live in-process owner) and marks them `interrupted`, cascading any of their `generation_run_items` in `pending` or `running` status to `interrupted`. The run-detail UI surfaces a **Resume** affordance that calls `POST /api/v1/runs/{run_id}/resume`, which starts a *fresh* run with a new `run_id` (new `generation_runs` row, `parent_run_id` set to the original) over only the unfinished items (the original run remains in history as `interrupted`).
  - **"Retry this sentence"** (Designer Flow 4 error state): a retry is a **fresh single-sentence run with a new `run_id`** (`parent_run_id` set to the original failed run) — it does not re-execute within the original run. The original failed `generation_run_items` row stays in its run for history; the retry is a new row in a new run.
  - Boundary: only writes to `generation_runs`, `generation_run_items`, `source_snapshots`, and `claude_candidates`; never mutates source or overlay tables.

- **Web UI (`web/`)**: React + TypeScript with Vite. Two build modes from one component tree:
  - **dev/local mode** — talks to `http://localhost:8000/api/v1`, full read+write affordances.
  - **static mode** — build-time SSG; reads pre-rendered JSON; authoring components are **stripped out at Vite build time** (not merely hidden) via a `STATIC=true` build-time flag plus a Vite `define` constant; the `<AuthOnly>` wrapper compiles to `null` in static mode and tree-shaking removes the wrapped imports, so the static bundle contains **no authoring component code and no write-endpoint URLs**. (No API-key strip-out concern: this repo never holds an Anthropic API key — generation runs through the local `claude` CLI subprocess, authenticated by Claude Code's own session.)
  - Data fetching uses **TanStack Query** as the canonical layer (caches reads, integrates cleanly with `If-Match`/version-aware mutations, and supports the SSE-backed run-detail page via a custom subscriber that feeds query cache invalidations). Routes mirror Designer's nav: `/read`, `/red-letters`, `/generate`, `/rank`, `/gsv`. Shared component library under `web/components/`. Boundary: never imports server-side code; talks to the API over HTTP only.

- **Static-site builder (`scripts/build_static.py`)**: Reads SQLite via the **service-layer functions** (`api/<feature>/service.py`) directly — not the FastAPI route handlers, not the running app. The same Pydantic response models that the API uses to serialize HTTP responses serialize the JSON snapshots written under `dist/api/v1/**/*.json`. Then runs Vite's static build with `STATIC=true`. Output: `dist/`. Calling the service layer directly avoids spinning up an in-process FastAPI client (and the routing/middleware overhead it brings) while preserving the single-contract guarantee — the service functions are the canonical implementation, and the routes are a thin adapter. The same builder is invoked by both `make build-static` and the in-UI **Build static site** button (see Contracts → `POST /api/v1/admin/build-static`). Boundary: read-only on SQLite; writes only to `dist/`; never touches the network.

- **Make targets (`Makefile`)**: `make import`, `make dev` (FastAPI + Vite dev server), `make export-gsv`, `make build-static`, `make test`. Boundary: orchestrates the components above; contains no logic of its own beyond shell glue.

### Contracts

- **HTTP API → web UI**: JSON over HTTP, all schemas Pydantic, OpenAPI auto-generated at `/docs`. Versioned under `/api/v1/*`. Concurrency control (v1): writes to rankings, red-letter overlays, tie-break decisions, **and `hidden_combos` (hide / unhide)** carry an `If-Match` header with the resource version; mismatches return `409 Conflict` with the current server version in the body so the UI can surface the conflict modal (per Designer's error states). Reads are unconditional. Errors return a typed `ErrorResponse` Pydantic model — `{code: str, message: str, details: dict | None}` — never bare strings.

- **Admin endpoints (`api/admin/`)**:
  - `GET /api/v1/admin/fixture-status` — `response_model=FixtureStatusResponse { disk_manifest_hash: str, db_fixture_version: str, stale: bool, last_imported_at: str }`. Called by the Designer status pill on every page load (and on a low-frequency poll while the UI is open) to decide whether to surface the **Re-import fixtures** affordance. `stale` is `disk_manifest_hash != db_fixture_version`. `disk_manifest_hash` is recomputed from `fixtures/manifest.json` on every request (cheap — one file hash); `db_fixture_version` and `last_imported_at` come from the `fixture_version` row written by the importer. Read-only; no auth.
  - `POST /api/v1/admin/reimport` — request body `ReimportRequest { force: bool = False }`; `response_model=ReimportResponse { fixture_version: str, files_imported: int, sentences_built: int, words_built: int, red_letter_source_ranges: int, orphans_detected: int, took_ms: int, log_path: str }`. Invokes the same code path as `make import`. On orphan detection without `force`, returns `409` with `{code: "orphans_detected", details: { orphan_summary: OrphanSummary }}` where `OrphanSummary` is the Pydantic model pinned in the `OrphanSummary schema` bullet below. Used by Designer's stale-fixture status-pill action; the orphan-resolution screen consumes `details.orphan_summary` directly.
  - `POST /api/v1/admin/build-static` — request body `BuildStaticRequest { include_unranked_placeholders: bool = True }`; `response_model=BuildStaticResponse { dist_path: str, files_written: int, coverage: BuildStaticCoverage, took_ms: int }`. Invokes the static-site builder via the service layer. Used by Designer's in-UI **Build static site** button; `make build-static` calls the same builder function directly. `BuildStaticCoverage` semantics are pinned in the `BuildStaticCoverage semantics` bullet below.

- **`OrphanSummary` schema** (Pydantic, returned in the `409 orphans_detected` body's `details.orphan_summary`; consumed by Designer's orphan-resolution screen and produced by the importer's abort path):
  - `OrphanSummary { affected_candidates: list[OrphanCandidate], affected_rankings: list[OrphanRanking], affected_overlays: list[OrphanOverlay], total: int }` where `total = len(affected_candidates) + len(affected_rankings) + len(affected_overlays)`.
  - `OrphanReason` (enum, shared by all three variants): `sentence_text_changed | sentence_removed | sentence_id_remapped`. The reason is the source-text diff that made the row orphan; it's surfaced verbatim in the orphan-resolution screen so Gavin knows why each disposition is needed.
  - `OrphanCandidate { candidate_id: int, sentence_id_old: str, sentence_id_new: str | None, reason: OrphanReason, style_prompt_version: str, source_set_id: SourceSetId, model: str, generated_at: str, candidate_text_excerpt: str, old_sentence_text_excerpt: str, new_sentence_text_excerpt: str | None, suggested_remap_sentence_id: str | None }` — `*_excerpt` fields are first-200-chars truncations included so the UI can render a remap/keep/delete decision card without a second fetch; `suggested_remap_sentence_id` is the importer's best-effort heuristic match (verse-range overlap + Greek-text similarity), null when no plausible remap exists; `sentence_id_new` is non-null only for `sentence_id_remapped`.
  - `OrphanRanking { sentence_id_old: str, sentence_id_new: str | None, reason: OrphanReason, ranked_candidate_count: int, has_notes: bool, has_tie_break: bool, version: int, suggested_remap_sentence_id: str | None }` — `version` is the OCC version of the existing ranking row (so a remap disposition can replay the `If-Match` flow against the new sentence row).
  - `OrphanOverlay { overlay_id: int, range_start_sentence_id_old: str, range_end_sentence_id_old: str, reason: OrphanReason, origin: "berean" | "manual", rejected: bool, suggested_remap_start_sentence_id: str | None, suggested_remap_end_sentence_id: str | None }` — orphans are reported per overlay range row, not per parent chain.
  - All three variants name the orphaned ID(s), the `OrphanReason`, and the user-visible context the resolution screen needs to render *remap / keep / delete* without further server round-trips. The follow-up `POST /api/v1/admin/reimport` with `force=true` carries the user's per-orphan dispositions in a `dispositions` field on the request body (data-engineer territory in PLAN; the contract here is that the 409 body fully describes the input).

- **`BuildStaticCoverage` semantics (pinned, v1)**: `BuildStaticCoverage { ranked: int, total: int, ch5_ranked: int, ch5_total: int }`. The denominator `total` is **the count of red-letter sentences in Matthew** (effective set = `red_letter_source_ranges ∪ red_letter_overlay_ranges` with `rejected=true` overlays subtracted); `ch5_total` is the same restricted to chapter 5. `ranked` / `ch5_ranked` are the subsets of those denominators that have a saved ranking with at least one non-hidden ranked candidate (i.e. the sentence has a ranking row and it would render with a winner, not as `— unranked —`). This denominator is chosen because v1 ranking targets red letters first per Manager DoD; using "all SBLGNT sentences" or "all sentences with at least one candidate" would either understate Gavin's progress against the DoD (every sentence has open-source candidates from import alone) or report 100% before any ranking happens. **v2 may extend the denominator** if non-red-letter ranking enters scope — at that point `BuildStaticCoverage` either grows additional fields (e.g. `total_all_sentences`) or its existing `total` is reinterpreted under a versioned response model. Designer's Flow 6 step 2 coverage indicator and the in-UI build-result block read these fields verbatim; both surfaces inherit this denominator definition.

- **Importer → SQLite**: A single transaction per run. Pre-flight check: every overlay-table foreign key resolves under the new fixture set; if not, abort with a structured report unless `--force`. Post-import: write a `fixture_version` row (manifest hash + import timestamp) consumed by the API's status pill. The same code is invoked from CLI and from `POST /api/v1/admin/reimport`.

- **Sentence identity**: Stable sentence IDs of the form `mat-${chapter}-${ordinal}` where ordinal is the 1-indexed SBLGNT-sentence position within the chapter. SBLGNT is the canonical edition for sentence boundaries; Byzantine is verse-keyed only (no Byzantine sentence rows in v1). ID stability across fixture upgrades is best-effort — re-segmentations that change the SBLGNT sentence count are a fixture-version bump and trigger the orphan flow.

- **Word identity**: `(sentence_id, ordinal)` is the natural key into the `words` table; word offsets in the range editor's coordinates refer to this `ordinal`. See Components → Word tokenizer for the deterministic tokenization rule.

- **Red-letter range model**: Two tables. `red_letter_source_ranges` (immutable from fixture, populated in v1 from the hand-curated fixture) and `red_letter_overlay_ranges` (mutable). The effective set is computed at read time as `source ∪ overlay` with overlays able to mark a source range `rejected=true`. Range coordinates are `(start_sentence_id, start_word_offset, end_sentence_id, end_word_offset)` anchored on **SBLGNT** word ordinals (the `words.ordinal` column). Overlay rows carry `origin` (`berean` | `manual`), `rejected` flag, `created_at`, and a `parent_overlay_id` chain for modification history.

- **Claude candidate identity**:
  - **Primary key**: a surrogate `candidate_id` (autoincrement integer; UUID is acceptable but integer is preferred for human-readable URLs and JSON). All foreign-key references (rankings, tie-break decisions) use `candidate_id`.
  - **Provenance attributes** (non-unique composite index for query): `(sentence_id, style_prompt_version, source_set_id, model, generated_at)` where `generated_at` is a UTC ISO-8601 timestamp. These five fields are still the candidate's *displayed* identity per Designer Flow 4 step 6, but they are no longer the database key — the surrogate `candidate_id` removes any millisecond-collision concern when two regenerations land in the same tick.
  - **Re-generation semantics unchanged**: same `(sentence, prompt, source_set_id, model)` produces a new row with a new `candidate_id` and a new `generated_at`. No overwrite.
  - **`source_set_id` enum** (v1, locked): `SBLGNT_ONLY`, `BYZ_ONLY`, `BOTH_GREEK`, `GREEK_PLUS_BIB`, `GREEK_PLUS_BLB`, `GREEK_PLUS_BSB`, `ENGLISH_ONLY_BSB`. **No `*_PLUS_WEB` variants** — WEB is display-only per Manager. Adding `GREEK_PLUS_WEB` later is a non-breaking enum extension.
  - **Resolved source documents** are stored content-addressed (see `source_snapshots` below); the candidate row carries a `source_snapshot_hash` foreign key, not the bundle itself.

- **Resolved source documents (`source_snapshots`)**: The bundle of source documents passed to Claude (e.g. SBLGNT span, Byzantine verses, BIB rows, BLB rows) for a given candidate can be tens of KB; multiple regenerations of the same sentence under the same combo produce the same bundle. Stored content-addressed:
  - Schema: `source_snapshots(snapshot_hash TEXT PRIMARY KEY, sentence_id TEXT NOT NULL, source_set_id TEXT NOT NULL, fixture_version TEXT NOT NULL, prompt_version TEXT NOT NULL, payload_json TEXT NOT NULL, byte_size INT NOT NULL, created_at TEXT NOT NULL)`.
  - `snapshot_hash` is the SHA-256 of the canonicalized `payload_json`.
  - **Canonicalization rule (pinned, must be byte-identical across Python versions and library updates)**:
    1. Encoding: UTF-8, with **`ensure_ascii=False`** (Greek text is emitted as raw UTF-8 codepoints, not `\uXXXX` escapes — escape policy is "no escaping beyond JSON's required minimum: `\\`, `\"`, and the control characters U+0000..U+001F").
    2. Object keys: sorted lexicographically by codepoint (Python's default sort order on `str`); applied recursively to every nested object.
    3. Separators: `(",", ":")` — no insignificant whitespace anywhere (no spaces after `:` or `,`, no trailing newline).
    4. Numbers: **integers only** in source bundles. Floats are explicitly disallowed — if a future bundle field would naturally be a float (e.g. an alignment confidence), it must be serialized as a string or a fixed-precision integer. Rationale: float-to-string round-tripping is not stable across Python minor versions (`repr` rules have shifted historically) and a single byte difference invalidates the SHA-256.
    5. Greek text normalization: **NFC** (`unicodedata.normalize("NFC", s)`) applied to every Greek string field before serialization. SBLGNT and Byzantine fixture text are NFC-normalized at import time; this rule is a defence-in-depth assertion at snapshot-build time.
    6. Booleans: lowercase `true` / `false`. Null: lowercase `null`. (JSON defaults — called out so no library quirk substitutes Python `True` / `None` reprs.)
    7. Reference implementation: `json.dumps(payload, ensure_ascii=False, sort_keys=True, separators=(",", ":"), allow_nan=False).encode("utf-8")` over an NFC-normalized, integer-only Python dict. `allow_nan=False` enforces the no-floats rule by raising on `nan` / `inf`.
  - The canonicalization rule above is a **versioned contract**: it is recorded in `fixtures/manifest.json` as `source_snapshot_canon_version: "v1"`. Any change is a fixture-version bump and re-snapshots all bundles.
  - The candidate row stores `source_snapshot_hash` as a FK to `source_snapshots.snapshot_hash`. Multiple `claude_candidates` rows referencing the same hash share storage.
  - Insertion is upsert-on-hash: the importer/runner computes the hash, inserts the row only if absent, then writes the candidate row. Snapshots are never mutated.
  - Trade-off in favour of this layout is recorded in Trade-offs (content-addressed dedupe).

- **Hidden-candidate persistence (`hidden_combos`)**: Designer Flow 5 promises that hiding a Claude card persists across regenerations of the same combo. Surrogate `candidate_id` makes a per-row `hidden_bool` insufficient — a regenerated identical combo gets a new `candidate_id` and would resurface. To honour Designer's user model we add a sentence-level "hidden combo" predicate:
  - Schema: `hidden_combos(sentence_id TEXT, style_prompt_version TEXT, source_set_id TEXT, model TEXT, hidden_at TEXT NOT NULL, version INT NOT NULL, PRIMARY KEY (sentence_id, style_prompt_version, source_set_id, model))`.
  - Effective hide rule (read path): a Claude candidate is hidden in the rank UI if **either** its row's `hidden_bool` is true (a one-off hide, e.g. a translation card or a one-off Claude row before this predicate existed) **or** a row exists in `hidden_combos` matching the candidate's four-tuple.
  - Unhide is a delete from `hidden_combos` (and a flip of any per-row `hidden_bool` for the same combo, in one transaction). **Both hide and unhide are OCC-protected writes**: the `version` column drives `If-Match` so an unhide in one tab doesn't get clobbered by a stale hide from another (uniform with rankings, red-letter overlays, and tie-break decisions per the OCC paragraph above and Hard decision #12).
  - Hidden Claude candidates still count toward "has Claude candidates" for the rank-queue filter (per Designer Flow 5 #3) — the filter joins `claude_candidates` directly, ignoring the `hidden_combos` predicate.
  - This is the Architect choice between Designer's option (a) sentence-level combo predicate and option (b) per-candidate hide-and-resurface; we picked (a) so Gavin doesn't re-hide the same dud combo on every regeneration. Designer's Flow 5 wording stands as written.

- **Ranking model**: Per sentence, a list of `(candidate_ref, rank, tied_with_above_bool, hidden_bool)` rows plus an optional notes string. `candidate_ref` is a discriminated union — `{kind: "translation", name: str, verse_range: str}` or `{kind: "claude", candidate_id: int}`. Ties are first-class (per Designer's tie support). A single monotonically incrementing `version` column on the per-sentence ranking row drives the `If-Match` concurrency check, and **explicitly covers the notes string as well as the rank list** — i.e. a notes-only edit and a rank-only edit in two browser tabs conflict against each other and surface the conflict modal. This is intentional: the ranking row (rank list + ties + notes) is one logical save unit, not two independently versioned siblings. Data engineer must not split notes into a sibling table assuming independent versioning.

- **Tie-break decisions**: Stored in a `tie_break_decisions` table keyed by `(sentence_id, resolved_at)` with `winner_ref` (same discriminated union as `candidate_ref` above), `tied_against` (JSON array of candidate refs that lost the tie-break), `resolved_at` (ISO-8601 UTC), and a `version` column for `If-Match`. The decision flows directly into GSV export as a `tie-broken` provenance variant.

- **`RunScope` discriminated union** (Pydantic, used by `CreateRunRequest` below; mirrors Designer Flow 4 step 2's four scope kinds):
  - `{kind: "one_sentence", sentence_id: str}` — a single sentence ID (e.g. `mat-5-3`).
  - `{kind: "verse_range", chapter: int, start_verse: int, end_verse: int}` — every SBLGNT sentence whose verse range intersects `[chapter:start_verse, chapter:end_verse]`. Cross-chapter ranges are **not** supported in v1 (mirrors the range-editor cross-chapter rule); the runner rejects with `400 invalid_scope` if `start_verse > end_verse` or chapter is out of range.
  - `{kind: "whole_chapter", chapter: int}` — every SBLGNT sentence in that chapter (1–28).
  - `{kind: "all_unranked_red_letter", as_of: str}` — every red-letter sentence (effective set) with no saved ranking as of an ISO-8601 UTC timestamp captured by the server when the run was created. The timestamp is recorded in `generation_runs.scope_json` so a Resume from this scope expands the same sentence set; it does not re-evaluate "unranked" against current state.
  - `RunScope` is the discriminator-on-`kind` type in `api/generate/schemas.py`. The runner expands it to a concrete ordered `list[str]` of sentence IDs at run-creation time and persists that expansion as the per-sentence `generation_run_items` rows.

- **`generation_runs` schema** (one row per run; the run-level envelope):
  - `generation_runs(run_id TEXT PRIMARY KEY, status TEXT NOT NULL, scope_json TEXT NOT NULL, style_prompt_version TEXT NOT NULL, source_set_id TEXT NOT NULL, model TEXT NOT NULL, created_at TEXT NOT NULL, started_at TEXT, completed_at TEXT, parent_run_id TEXT)`
  - `status` enum: `pending | running | completed | failed | cancelled | interrupted`. `interrupted` is set on startup for any `running` row with no live in-process owner (per Components → Generation runner).
  - `scope_json` stores the original `RunScope` (so Resume can replay the sentence-set rule, e.g. the `as_of` timestamp for `all_unranked_red_letter`).
  - `parent_run_id` is set on Resume runs and on per-sentence Retry runs (Designer Flow 4 error state); null otherwise. The original run is preserved as history.

- **`generation_run_items` schema** (one row per sentence within a run; the SSE-replay grain):
  - `generation_run_items(run_id TEXT NOT NULL, ordinal INT NOT NULL, sentence_id TEXT NOT NULL, status TEXT NOT NULL, candidate_id INT, error_code TEXT, error_message TEXT, started_at TEXT, completed_at TEXT, PRIMARY KEY (run_id, ordinal), FOREIGN KEY (run_id) REFERENCES generation_runs(run_id), FOREIGN KEY (candidate_id) REFERENCES claude_candidates(candidate_id))`
  - `status` enum: `pending | running | completed | failed | cancelled | interrupted`.
  - `candidate_id` is non-null only when `status = completed`; on failure it is null and `error_code`/`error_message` are populated.
  - **`ordinal` density (pinned)**: **dense, contiguous `1..N`** where `N` is the number of sentences in the run's resolved scope at run-creation time (the expansion of `RunScope` into a concrete `list[str]` of sentence IDs). No gaps, no sparseness, no reuse — the row at `ordinal=k` is the `k`-th sentence in the canonical order produced by `RunScope` expansion. Cancelled / interrupted / failed items keep their original ordinal (status changes, ordinal does not). A Resume run is a *new* run with its own dense `1..M` over the unfinished slice — the original run's ordinals are not renumbered. This matters for Resume (the new run starts at `ordinal=1`, not at the original's `last_completed_ordinal+1`) and for replay (the SSE replayer can iterate `for k in range(1, N+1)` without holes).
  - `ordinal` is the canonical SSE-replay order; on `GET /runs/{run_id}/stream` the server replays rows in `(run_id, ordinal)` order before attaching the live tail. **This is the SSE-replay contract** — Reliability and Data engineers do not negotiate it in PLAN.
  - `error_code` is a coarse enum surfaced by the worktree runner: `claude_cli_unavailable | timeout | invalid_response | disk_full | internal`. The DB-level CHECK (per Data) also still permits the historical SDK-era values (`anthropic_api_error`, `anthropic_refusal`, `rate_limit`) as forward-compatible dead values; the worktree runner does not emit them. `error_message` is the human-readable detail surfaced to the UI.

- **Generation run streaming**:
  - `POST /api/v1/runs` — body `CreateRunRequest { scope: RunScope, style_prompt_version: str, source_set_id: SourceSetId, model: str }`; `response_model=CreateRunResponse { run_id: str, sentence_ids: list[str] }`. Starts the async runner; persists one `generation_runs` row plus one `generation_run_items` row per expanded sentence (`status=pending`).
  - `GET /api/v1/runs/{run_id}/stream` — SSE; emits `candidate_completed`, `candidate_failed`, `run_cancelled`, `run_finished`, `run_interrupted` events. On reconnect, replays prior events from `generation_run_items` rows in `ordinal` order before attaching live tail (see Components → Generation runner).
  - `POST /api/v1/runs/{run_id}/cancel` — stops further dispatch; in-flight Claude calls finish; sets `generation_runs.status = cancelled` and any unstarted `generation_run_items.status = cancelled`.
  - `POST /api/v1/runs/{run_id}/resume` — starts a fresh run (new `run_id`, `parent_run_id` set to the original) over the unfinished `generation_run_items` from a cancelled or interrupted run, returns a new `run_id`.

- **GSV export contract**: `gsv.json` schema is the load-bearing artifact. Each entry: `{sentence_id, verse_range, text, provenance}` where provenance is a discriminated union on `kind`:
  - `{kind: "translation", name, verse_range}`
  - `{kind: "claude", candidate_id, style_prompt_version, source_set_id, model, generated_at}`
  - `{kind: "tie-broken", winner: <translation | claude variant above>, tied_against: [<refs>], resolved_at}`
  - `{kind: "tie", candidates: [...], unresolved: true}` (structured/Markdown export only — plain-text export refuses to write while unresolved ties exist)
  The `source_set_id` field name matches the enum used in `CreateRunRequest` and the `claude_candidates` row — there is no `source_set` alias anywhere in v1 contracts. This contract is a Pydantic model in `api/gsv/schemas.py`; the export script, the GSV view, and the static-site builder all consume the same model.
  - **Three export formats** in v1 (`response_model` `GsvExportResponse` returns the chosen format as a string body or JSON object):
    1. **Plain text** — `gsv.txt`, prose only, `chapter:verse` markers, no provenance.
    2. **Structured JSON** — `gsv.json`, the schema above.
    3. **Markdown** — `gsv.md`, chapter headers (`## Matthew 5`), one paragraph per sentence with verse markers preserved (e.g. `**5:3**`), and per-sentence provenance footnotes (`[^mat-5-1]: Claude · literal-v1 · BOTH_GREEK · claude-... · 2026-05-03T...`).

- **Fixture manifest format**: `fixtures/manifest.json` is a Pydantic-validated document — `{version: str, files: [{name, path, source_url, retrieved_at, release_tag, sha256}], segmenter: {edition: "sblgnt", rule: "sblgnt-punctuation-v1"}, byzantine_mode: "verse-only-v1", word_tokenizer: "greek-letters-with-clitics-v1", prompts: [...]}`. The manifest version bumps when any file's hash or any rule string changes; that's how the API's status pill knows to flag a stale DB.

- **Prompt artifact format**: `fixtures/prompts/${name}-v${n}.md` — front-matter block (YAML: `name`, `version`, `description`, `requires_greek: bool`, `compatible_source_sets: [...]`) plus a markdown body that is the prompt template. Templates use `{{greek_sblgnt}}`, `{{greek_byz}}`, `{{bib_interlinear}}`, etc.; the Claude client validates every placeholder against the chosen source set before calling the API.

- **Static-site JSON contract**: `dist/api/v1/**/*.json` mirrors the live API's read responses 1:1. The files are produced by calling the **service layer** directly (not the FastAPI app), serialized through the same Pydantic models. The static UI uses an HTTP client shim that resolves URLs to file paths. Components don't know whether they're talking to a server or a JSON tree.

### Integrations

- **Claude Code CLI**: The only external dependency for generation. Invoked as a subprocess (`subprocess.Popen`) per sentence with `cwd` set to a fresh git worktree under `data/worktrees/{run_id}/{ordinal}/` and arguments `-p --model claude-opus-4-7 --effort xhigh --output-format text` (model + effort are settings; the listed values are the v1 defaults). The prompt body + canonicalised source bundle + sentence meta are passed as the `-p` positional. **No HTTP outbound from this repo** — the `claude` CLI uses Gavin's already-logged-in Claude Code subscription. **No `ANTHROPIC_API_KEY` plumbing** — the trust boundary for generation is Claude Code's own OS-level session; this repo never sees a key. Output: stdout. For prompts whose front-matter declares `output_format: json` the runner JSON-parses stdout (after stripping any triple-backtick fences); for `output_format: text` stdout is stored verbatim. No retries; a failed subagent is a UI-surfaced error per Designer. No streaming from the subagent to the UI — we wait for the subprocess to terminate, persist, then push a single SSE event per completion. (Streaming the subagent's output token-by-token would require parsing in flight; Gavin wants reproducible candidates, not a typing animation.) The runner sanity-checks `claude --version` at run-creation time and rejects with `code='claude_cli_unavailable'` if the CLI isn't reachable. The scope summary (Designer Flow 4 step 3) does **not** spawn any subagent in v1 — see Components → Worktree spawner.

Source-of-truth file: `https://bereanbible.com/bsb_tables.txt` (or the equivalent zipped distribution `bsb_tables.zip`); SHA-256 pinned in `fixtures/manifest.json`.

### Trade-offs

- **SQLite over Supabase/Postgres**: Chose SQLite because (a) one user, one device, no concurrent writers; (b) the database is rebuildable from fixtures, so durability beyond the local disk is not a concern; (c) version-controlled fixtures + a deterministic importer give us the reproducibility benefit Postgres-with-migrations would give us, without the operational overhead. Cost: if this ever becomes multi-user we throw the storage layer away. Acceptable — multi-user is explicitly out of scope and the repository layer is the only place that knows about SQLite.

- **FastAPI over a thinner local server**: Chose FastAPI despite the single-user framing because the global rules already mandate Pydantic `response_model` everywhere and the `/docs` surface is genuinely useful when iterating on the static-export contract (the same schemas drive both). A pure-Flask or hand-rolled WSGI server would save no meaningful complexity and lose schema enforcement.

- **React + Vite over a server-rendered framework (Next.js, Remix)**: Chose Vite + React because the static-site requirement is "render JSON snapshots into HTML" — Vite's static build does this without us adopting a server framework whose runtime we'd then have to strip out for the static target. Next.js would work but its hosting model assumes a Node runtime in production; we want a flat directory of files. Cost: we write a tiny HTTP-client shim for the static mode. Acceptable.

- **TanStack Query for client data fetching**: Picked over a hand-rolled fetch layer because rankings + red-letter overlays need cache-invalidation discipline (post-mutation, refetch the affected sentence; on `409` the conflict modal needs the freshest server version). TanStack Query gives us that for free, and it composes cleanly with `If-Match` headers and SSE-driven cache updates.

- **`sse-starlette` for the SSE integration**: Picked over a hand-rolled `EventSourceResponse` because it handles disconnect detection, ping cadence, and graceful shutdown out of the box, and it's the de facto FastAPI SSE library.

- **No ORM**: Chose raw SQL through a thin repository layer because the schema is small, the queries are mostly sentence-keyed lookups, and ORM lazy-loading would obscure the read paths the static builder depends on. Cost: a few hand-written queries. Acceptable.

- **In-process worktree subagent generation, not Modal**: The global stack defaults Claude/long jobs to Modal. Overridden because (a) Gavin runs this on his own machine using his already-logged-in Claude Code subscription — there is no API key the worker would need; (b) batch sizes are at most one chapter (~100 sentences); (c) the `claude` CLI must be invoked locally (it's tied to the OS session); (d) introducing a serverless tier means introducing auth between local UI and the worker, plus a deployment story. SSE from FastAPI handles progress just fine. Cost: if Gavin closes his laptop mid-run, the run aborts; orphaned `running` rows are detected on startup and the UI offers Resume. Acceptable — the candidates that *did* land are persisted, and the worktrees clean themselves up via `sweep_stale_worktrees` at startup.

- **Static-site builder calls the service layer directly (not the FastAPI route handlers)**: An earlier draft proposed invoking the route handlers in-process to maximize "single source of truth." Rejected: routing/middleware/dependency-injection adds cost and obscures errors during a build, and the Pydantic models — not the handlers — are the actual contract. Calling `api/<feature>/service.py` functions directly preserves the single-contract guarantee while keeping the build fast and stack traces shallow. Cost: routes must remain thin adapters over service functions (this is a discipline, enforced in code review and in PLAN's testing strategy).

- **Surrogate `candidate_id` over the natural five-tuple**: Considered making `(sentence_id, style_prompt_version, source_set_id, model, generated_at)` the primary key. Rejected because two regenerations within the same millisecond would collide, and because integer FKs in `rankings` and `tie_break_decisions` are smaller and easier to read in URLs and JSON. The five-tuple is preserved as the *displayed* identity per Designer Flow 4 and as a non-unique composite index for query.

- **Content-addressed `source_snapshots` over inline JSON or a per-candidate join table**: For long discourses (e.g. Sermon on the Mount sentences with `BOTH_GREEK + BIB`), the resolved-source bundle is tens of KB; multiplied across hundreds of candidates and many regenerations of the same combo, an inline JSON column or a 1:1 join table both balloon storage and obscure the dedupe relationship. Considered (a) inline JSON column, (b) `candidate_sources` 1:1 table, (c) content-addressed via SHA-256. Picked **(c)**: the bundle is keyed by `(prompt_version, source_set_id, sentence_id, fixture_version)` semantically, but the SHA-256 of the canonical JSON is the actual key — multiple regenerations of the same combo (which always produce the same bundle) share one row. Cost: an upsert-on-hash insertion path and a join to read the bundle back. Acceptable — the dedupe ratio is high and the join is one-hop.

- **Hidden-combo predicate over per-row `hidden_bool` only**: Designer Flow 5 promises that hiding a Claude card persists across regenerations of the same combo. With surrogate `candidate_id`, a per-row `hidden_bool` does not survive regeneration (the new row gets a new `candidate_id` and surfaces unhidden). Considered (a) sentence-level "hidden combo" predicate, (b) reframe semantics so Gavin re-hides the same combo on every regeneration. Picked **(a)** — matches Designer's user model and prevents repeated re-hiding of the same dud combo. Cost: an extra small table (`hidden_combos`) and a slightly more complex effective-hide rule (per-row OR predicate). Acceptable.

- **Byzantine sentence-level alignment deferred (verse-only in v1)**: Considered (a) committing to the Byzantine 2018 edition's punctuation directly with a parallel `byzantine_sentences` table, and (b) deferring entirely. Picked **(b)**. Reasons: Manager DoD targets SBLGNT for ranking and GSV (Byzantine is reference text); a parallel sentence model doubles the schema surface area for the range editor and the parallel reader's `↔` boundary glyph for marginal v1 value; verifying punctuation parity across Byzantine editions is a side quest. Trade-off accepted: Byzantine appears in the parallel reader and detail drawer at verse granularity, with the existing `↔` divergence glyph still firing whenever an SBLGNT sentence's verse range crosses an obvious Byzantine sentence break. If we later need Byzantine sentence-level alignment, it ships as additive tables.

- **Word-level alignment anchored on SBLGNT, deterministic Greek-letter tokenizer**: Pinned a specific tokenization rule (Components → Word tokenizer) so the range editor and BIB alignment have a single coordinate system. Considered using a third-party tokenizer (CLTK, spaCy-greek). Rejected: another dependency for a 28-chapter corpus where the rule fits in a regex.

- **Hand-curated red-letter source fixture in v1, Berean importer deferred**: Berean's red-letter status is a verification item. Picked the conservative path: ship a hand-curated `red_letter_source_ranges` fixture covering Matthew 5 (DoD floor) and any further chapters Gavin curates before v1 cutover. If a machine-readable Berean red-letter dataset is later confirmed, an importer module replaces the fixture with no schema change. Cost: more upfront curation work. Acceptable — the alternative is a TODO that blocks the DoD.

- **No cost estimation in v1; subscription-bounded usage**: The earlier draft pre-computed a USD cost-band (character-count heuristic ±20%) before dispatching. Worktree-subagent generation runs against Gavin's existing Claude Code subscription — there is no per-token billing this repo can or should account for. The Flow 4 scope summary instead reports the resolved sentence count and a wall-clock estimate (median latency × N / `MAX_CONCURRENT_WORKTREES`). Caps shift from dollars to worktree counts and rate (`MAX_WORKTREES_PER_RUN`, `MAX_RUNS_PER_DAY`, `MAX_CONCURRENT_WORKTREES`, `MAX_WALL_CLOCK_SECONDS_PER_SENTENCE`) — see PLAN §abuse. If a future Claude Code release surfaces a per-run usage signal we can present that pre-flight, but it is not on the v1 critical path.

- **Twin override pattern (`X-Twin-*`) waived in v1**: Per global CLAUDE.md, services typically must accept `X-Twin-{Dep}-Base-Url` headers in `env=development` to redirect outbound dependencies (used for evals). Waived here because (a) **there is no HTTP outbound from this repo at all** — the only generation-side dependency is the local `claude` CLI subprocess, which the twin pattern doesn't apply to (it's not a base URL); (b) the FastAPI app is bound to `127.0.0.1` with no inbound HTTP from external callers, so the SSRF concern that motivates the production gate doesn't apply; (c) the project is a single-user localhost-only tool — the user's stated waiver criterion. Documented here so a Phase 4 reviewer doesn't flag it. If we ever add a real HTTP-based outbound dependency or expose the API beyond loopback, revisit.

- **Sentence as the canonical SBLGNT unit, no separate Byzantine sentence model**: Considered making sentences edition-independent (separate sentence IDs per edition with a mapping table). Rejected because every downstream surface (ranking, GSV, drawer) needs *one* primary unit to anchor the UI, and per the deferral above Byzantine is verse-keyed in v1 anyway. Cost: when a Byzantine "sentence" would map to multiple SBLGNT sentences, ranking still happens per SBLGNT unit and the divergence is only signaled visually. Acceptable for v1.

- **Overlay model for red letters as append-only mutation chain**: Considered destructive edits (one current row per range, history in a separate audit table). Rejected because Designer's "Original diff toggle" requires the unmutated source to be one query away, and an append-only overlay chain plus a `parent_overlay_id` makes that trivially `LEFT JOIN red_letter_overlay_ranges ON …`. Cost: more rows. Acceptable — the volume is tiny.

- **SSE for generation progress over WebSockets**: One-way server→client, browser refresh resumes by replaying `generation_run_items` rows in `(run_id, ordinal)` order then attaching to the live tail, no extra protocol. WebSockets would let us push UI events from server to client too, but we don't have any. Cost: SSE has fewer toys. Acceptable — we don't need them.

- **Static-site JSON snapshots over a shared rendering pipeline**: Considered server-rendering the static site with the live FastAPI app and snapshotting HTML. Rejected because then the static UI's authoring strip-out happens at HTML-generation time and we lose the ability to evolve the components freely. JSON snapshots + a unified component library + Vite-time `<AuthOnly>` strip-out means the components don't change between modes — only the data source does. Cost: an extra build step. Acceptable.

- **Optimistic concurrency control in v1, not deferred**: Manager pinned this. Rankings, red-letter overlays, and tie-break decisions all carry a `version` column; writes use `If-Match`; conflicts surface a UI modal. Cost: one extra column per overlay/ranking table and a tiny middleware for `If-Match`. Acceptable — silent last-write-wins on rankings is the failure mode that would cost Gavin the most work to recover from.

### Hard architectural decisions to lock in for v1

These are the choices that, if changed later, force a rewrite of multiple components. We commit to them now:

1. **SBLGNT is the canonical sentence-boundary edition.** All sentence IDs, range coordinates, alignments, and ranking units are anchored to SBLGNT. Byzantine ships as **verse-keyed reference text only in v1** — no Byzantine sentence rows. Sentence-level Byzantine alignment is deferred and would ship as additive tables. (This decision is the architectural counterpart to Manager's success criterion line 12, which states SBLGNT is the canonical sentence model in v1 and Byzantine ships verse-keyed only.)
2. **Sentence IDs are `mat-${chapter}-${ordinal}` and stable across non-segmenter fixture upgrades.** Re-segmentations are a versioned, opt-in event with an orphan-resolution UI.
3. **Word identity is `(sentence_id, ordinal)` over a deterministic Greek-letter tokenizer rule.** The `words` table is the single coordinate system used by the range editor (for `*_word_offset`) and by the BIB alignment (for `strong_id` lookup). The tokenization rule is pinned in the manifest as `word_tokenizer: "greek-letters-with-clitics-v1"` — changes are a fixture-version bump.
4. **Red-letter ranges are an append-only overlay chain on top of an immutable source set.** Effective set = source ∪ overlay; rejection is a flag, not a delete. The v1 source set is a hand-curated fixture; a Berean importer can replace it later without schema change.
5. **Claude candidates are immutable, identified by a surrogate `candidate_id` primary key.** The provenance attributes `(sentence_id, style_prompt_version, source_set_id, model, generated_at)` are stored on the same row, indexed for query, and surfaced as the displayed identity — but they are *not* the database key, eliminating the millisecond-collision risk. Re-generation creates a new row, never overwrites. The resolved source documents passed to Claude are stored content-addressed in `source_snapshots` (SHA-256 of canonical JSON) and the candidate row carries the snapshot hash as a foreign key, so identical-combo regenerations dedupe to one snapshot. `source_set_id` does not include any `*_PLUS_WEB` value in v1.
6. **The HTTP API is the only contract between the UI and the data.** The static site consumes the same contract via JSON snapshots produced by calling the **service layer** functions directly with the same Pydantic schemas. No second contract, no parallel data path.
7. **SQLite is the runtime store; fixtures are the durable store.** The DB is gitignored and rebuildable. Overlay tables are preserved across imports; source tables are not.
8. **No external dependency reachable from production-style hosts.** The local API is bound to `127.0.0.1`. The static site is read-only files. There is no server tier to attack. The `X-Twin-*` override pattern is therefore waived for v1 (Trade-offs).
9. **Word-level alignment is anchored on BIB's Strong's keys, applied to SBLGNT only.** v1 does not produce a word-level Byzantine↔English alignment; word operations on Byzantine are visibly best-effort (the `≈` glyph) and use sentence-aligned text fall-back.
10. **Generation happens in-process; progress streams over SSE (`sse-starlette`); runs are persisted in `generation_runs` (one row per run) plus `generation_run_items` (one row per sentence within a run, the SSE-replay grain).** SSE reconnect replays prior `generation_run_items` rows in `(run_id, ordinal)` order then attaches to the live tail; orphaned `running` rows on startup become `interrupted` and the UI offers Resume (a fresh run with a new `run_id` and `parent_run_id` pointing back). "Retry this sentence" is also a fresh run with a new `run_id`. No worker tier, no queue, no Modal.
11. **Style prompts are versioned fixture artifacts, not database rows.** Editing a prompt is a fixture change with a version bump; `${name}-v1` and `${name}-v2` are different prompts.
12. **Optimistic concurrency control via `If-Match` and `version` columns is in v1.** Applies to rankings, red-letter overlays, tie-break decisions, **and `hidden_combos` writes (hide / unhide)**. `409 Conflict` returns the current server version so the UI can resolve. The OCC list is uniform across every table that carries a `version` column — adding `hidden_combos` here closes the gap where the schema already carried `version` but the contract paragraph didn't enumerate it.
13. **GSV exports in three formats in v1**: plain text, structured JSON, and Markdown. All three share the GSV provenance Pydantic model (including the `tie-broken` provenance variant).
14. **Authoring code is stripped at Vite build time in static mode**, not merely hidden — the static bundle has no authoring components and no write-endpoint URLs. (No API-key strip-out concern: this repo never holds an Anthropic API key. Generation runs through the local `claude` CLI under Claude Code's own session.)
15. **Hidden Claude candidates persist by combo, not by candidate row.** A `hidden_combos` table keyed `(sentence_id, style_prompt_version, source_set_id, model)` suppresses any current or future candidate matching the four-tuple, so a regenerated identical-combo candidate stays hidden without Gavin re-hiding it (Designer Flow 5 promise). Per-row `hidden_bool` remains for one-off hides (e.g. a translation card) and the effective hide is the OR of the two predicates.
16. **Resolved source documents are stored content-addressed in `source_snapshots`.** Candidates reference a SHA-256 hash; identical-combo regenerations dedupe to one snapshot row. Snapshots are immutable.
17. **The ranking row (rank list + ties + notes) is one logical save unit with one `version` column.** A notes-only edit and a rank-only edit in two browser tabs intentionally conflict against each other; notes is not split into a sibling table with independent versioning.
